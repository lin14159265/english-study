# 阶段 1A：本地记录保留与可靠性修复

本次只实施 1A。基线为 `5c874ea03b2e57499ba26fd4948355a16caf711a`，完整个人学习数据同步仍是最终必须实现的目标。未接入 Firebase、创建云资源、开通 Blaze 或上传任何真实学习数据。

## 行为及数据保护

| 问题 | 修复后的行为 |
|---|---|
| 资料暂未加载、不可用或被移除 | currentKey、readKeys、positionKeys 保留完整稳定键；当前目录序号只用于显示，不反向过滤保存记录 |
| 缺失的当前文章 | 临时显示第一篇并提示资料未就绪，不把该篇滚动位置写成缺失文章的位置；资料就绪后按原键恢复 |
| 目录重排、已读取消 | 按稳定键重新映射；只改变用户操作的那篇，其他未加载文章的已读及位置不受影响 |
| 固定链接 | `#article-02`、`#read=...` 继续优先直达；未知稳定链接保留为待加载目标，不改写为第一篇链接 |
| 正在显示第一篇作为回退时打开 `#article-01` | 明确选择第一篇，解除待加载的导航目标；仍保留缺失文章的历史记录 |
| 无未保存修改的外页通知 | 从 IDB 的同一只读事务读取 workspace/current 与 packs，接收实际新头并刷新阅读器、学习状态及资料缓存；不自动切走当前可用文章或跳滚动位置 |
| 本页有未保存修改 | 保留本页内容并阻止写入外页的新头；提示导出本页备份后重新打开，重试不能静默丢草稿 |
| 广播丢失或不可用 | 页面获得焦点时再读取数据库头；最终写入仍检查 token，不允许旧页无条件覆盖 |
| 重复广播及未变化的数据 | 不产生额外提交；资料及个人修订未改变时，不因每个外页位置保存而重新编译整套文章 |
| 保存失败 | 原 IDB 提交及 localStorage 镜像保持不变；本页数据仍可备份，写入成功后才显示已保存 |

数据库名称仍是 `english-study.packages.v1`，版本仍为 2；没有清空、删除或重建数据库。原有恢复/回退功能的明确用户操作继续保留，不把这些操作用作本次升级迁移。legacy localStorage 键保留；旧数字阅读记录在文章可用时转换为稳定键，并保留数字字段兼容。

JSON 学习备份继续使用 version 1。新增可选 `reader.resumeKey`，预留直达路径与最后阅读现场的区分；没有新增首页续读入口或跨屏语义锚点，这些属于 1B。旧备份不要求该字段；新字段参与备份验证、明确优先的合并及独立副本引用重写。固定链接仍沿用原优先级，不承诺本轮已经实现 1B 的完整续读体验。

## 验证范围

执行 `node --test tests/*.test.cjs`。**105 项全部通过：原有 75 项检查全部保留，新增 30 项**。新增检查覆盖用户要求的缺失资料、异步加载、迁移、多标签页及保存失败。阅读器/学习 UI 使用实际源代码与最小 DOM、确定性计时器；存储使用可控事务替身；导入测试包含真正延迟解析的 fetch Promise，不只匹配源文件文字。

其中 4 个关键回归在旧 reader.js/workspace-store.js 上均失败：缺失当前键变成 original/1；资料到达后没有恢复目标；操作已读过滤未知键；干净外页进入永久 conflict。修复版通过这些行为检查。

真实浏览器暂未完成：Browser 插件不可用，已按前端测试技能尝试现有 Playwright；Chromium 启动失败，因为缺少对应可执行文件。没有安装浏览器或更改项目依赖，没有真实 DOM 布局、真实 IndexedDB 并发、Service Worker 生命周期、手机或平板的测试证据。VM 和事务替身不能替代这些检查。

## 合并前建议的真实端验收

使用本地独立预览或隔离测试 origin，先使用合成备份；不要清除正常站点数据。

1. 从根地址读第 7 篇中段，标记已读，确认已保存后重开；再打开 `#article-02` 验证直达。
2. 使用测试包的稳定键，延迟发布目录或临时移除本机可用副本；检查未知键保留，重新加载包后位置及已读恢复；期间不要把回退第一篇的位置写给目标文章。
3. 同一浏览器两个标签页：B 标记已读，A 没有未保存修改时接收更新；A 再保存应成功。交替操作，不应出现广播回写循环、自动跳篇或突然滚动。
4. A 输入草稿但尚未提交，B 提交不同状态；A 明确显示冲突，导出包含本页草稿，数据库保持 B 状态。导出后重新打开/按现有备份预览合并处理，不直接重试覆盖。
5. 拒绝 IDB 打开或注入事务失败，检查未保存提示及旧镜像不变；恢复写入能力后重试，旧已读与草稿仍在。
6. 使用旧 version 1 备份导入、导出、恢复与回退；检查来源引用与个人修订；允许未知来源存在，不能因为暂时无法定位而删除。
7. 验证旧 worker 控制页面时不会提前混入新脚本；确认更新后使用同版本资源，离线重开可读，IDB 不被清除。

电脑 Chrome/Edge、手机真实 iOS Safari、平板实际浏览器分别运行本机续读及关键导航；屏幕尺寸变化仍只按旧像素恢复，准确跨屏定位属于 1B，不列为 1A 已通过能力。

## 风险与回退

- 本次保留未来不可用的稳定键，因此备份可能包含缺失来源；这是保护记录，不是格式损坏。永久移除资料也不自动清掉学习历史。
- 已经由旧版本过滤并提交的记录不能凭空重建，只能从此前有效备份恢复。新代码保护仍存在的记录。
- 有真实未保存修改的页面仍可能进入冲突；这是必要保护，导出并重新打开后可继续，而非干净页永久失效。没有擅自引入学习记录的自动合并。
- 外页刷新读取 workspace 与资料快照，资料较大时仍有读取/序列化成本；内容未改变时跳过资料重编译。本轮不改现有整体 workspace 存储架构。
- 页面关闭最后位置仍依赖原有滚动防抖和 pagehide；持续保存、visibilitychange 与锚点优化留在 1B。手机强制结束进程不保证保存最后瞬间。
- 部署前先下载有效完整备份。PR 不自动合并或部署；合并后发布还需按上述真实端项目验证。
- 数据库版本未变，不需要降级或删库。若需代码回退，优先保留本次“稳定键不删除”的兼容修复，只撤回有问题的刷新路径，并发布新资源版本；直接回到旧基线会重新暴露过滤缺失记录的缺陷。
- 紧急回退前先备份并暂时关闭相关页面；在隔离环境用升级前备份验证恢复。不要为了回退清空正常 origin 的 IDB，也不要通过缓存清理删除学习数据。

## 后续 2B 的三个设计约束（仅设计，未实施）

### 1. 业务记录与 outbox 必须一起提交

在未来 IDB 增量版本中增加 syncOutbox 与 syncMeta 等 store；不删除旧 packs/workspace。先在内存计算操作候选；一个 readwrite 事务读取本机头与 syncMeta 计数器，检查基线，分配并持久保存 operationId/新计数器，同时写入绑定 uid/generation 的业务快照与 outbox。事务回调中不等待网络或其他异步计算。涉及私包的操作同时纳入 packs。禁止“先 StudyState.flush() 成功，再开另一个事务插入队列”；中途终止会产生本机已保存但永远没有上传操作的窗口。

事务成功后才更新提交 token、页面内存快照与“本机已保存”。失败全部回滚，操作保持未提交候选；恢复备份、回退、迁移及批量资料写入也走对应的统一事务边界。暂不在 1A 引入这些队列或数据库版本变化。

### 2. 云合并必须更新所有运行中的消费者

远端结果先与本机已提交头、未提交候选及 outbox 比较，生成合并计划；在本机事务中提交业务结果、云基线和队列确认。提交时检查本地 token，不能把等待网络期间用户新增的修改覆盖掉。冲突时重新计算或进入预览。

本机提交完成后，通过统一的版本化通知刷新 reader、learning、extra 及资料缓存；不得只改 IDB 而让旧闭包继续持有旧快照。刷新不回写旧状态、不产生上传回声、不自动跳走阅读现场。未保存编辑/草稿保留为候选，不能在“刷新 UI”时清空。1A 的 study-state-reloaded 是本地外页通知的基础；2B 仍需增加云基线、队列及运行中编辑的完整验证。

### 3. 持久幂等确认不能只保存 lastOperationId

每次操作先在本机原子事务中保存不可变 operationId，例如持久 deviceId + 持久单调计数；退出/重开、网络重试不重新生成。队列保存 uid、generation、操作内容摘要、baseRevision 及目标记录，不按最后一个 ID 猜测以前操作是否成功。

推荐云端 `users/{uid}/operations/{operationId}` 保存持久处理回执：操作摘要、结果、受影响记录的提交修订与服务端时间。联网时通过 Firestore 事务先读取回执和目标修订：已存在且摘要一致则返回既有结果；相同 ID 不同摘要拒绝；不存在才检查基线，并把业务变更与回执一同提交。客户端收到确认后，在本机事务中确认对应 outbox 项及云基线。上传成功但响应丢失后，用同一个 ID 查询/重试，不重复执行；拒绝/冲突也要有可识别的处理结果，不能在重试时偷换基线。

初期单人用量可保留全部回执；如果以后压缩，须保留设备序号确认范围、generation 和受支持的重放窗口，过旧设备重新校验，不能直接按 TTL 删除后允许旧操作再次执行。回执和实体规则只允许本人 UID，限制字段与摘要一致性；不在客户端放管理员凭据。这个方案需要规则与故障注入测试，不能因 SDK 具有离线缓存就宣布幂等已经完成。[Firestore 事务依据](https://firebase.google.com/docs/firestore/manage-data/transactions)

2A 可继续只读可行性研究。本轮没有 2B/3 的正式开发；完整同步的最终范围不因此改变。
