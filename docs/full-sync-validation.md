## 持续“同步中”排查与修复

- 已复现：SDK 请求未返回时控制器的 running 锁一直占用，手动重试只能标记下一轮；加入每个 Firestore 请求 30 秒应用层超时，释放本轮锁并保留持久 flight/outbox。超时不等于取消 SDK 写入，重试复用仍未完成的底层请求，并通过永久回执和版本 CAS 确认结果，避免重复提交。
- 已复现：上传及本机确认已完成后，必须等额外一轮拉取才显示已同步；改为安全确认同一业务快照且队列为空后立即显示已确认，后续无本机待上传的检查独立显示“已同步 · 检查更新”。后续拉取仍会应用其他设备的新版本；旧回执不代表云端没有更晚更新。
- 同一服务器 head 的重复元数据通知不再反复触发同步。状态明确给出检查版本、读取资料计数、上传、确认或本机应用阶段；某阶段超过 20 秒显示等待较久，页面恢复可见时重新检查等待提示并安排同步。
- 真实浏览器新增测试注入不返回的适配器请求，验证 20 秒提示、返回事件和按钮不产生并发拉取、失败不丢本机记录、恢复后重新同步。适配器单测分别注入真实 SDK 接口桩的挂起与晚到提交；这不是手机实际网络抓包。
- index 与 Service Worker 资源版本同步更新。保持 IndexedDB v3、version 1 备份、云端结构和 Security Rules；无需重新发布规则或重新导入私人资料。

## 大资料包成本

`tests/sync-benchmark.cjs` 在 Chromium 原生 IndexedDB 中使用 12 个合成私包，总计 21,023,450 UTF-8 字节（约 20.05 MiB），预热一次、各测五次。同一实现对比完整云端应用与仅上传回执确认：

| 本机阶段 | 中位耗时 | packs 全读 / 写入 | UI 重载 |
| --- | --- | --- | --- |
| 完整 `applySync` | 314.1 ms（304.3–334.0） | 1 / 12 | 1 |
| 仅回执 `confirmSync` | 146.1 ms（134.3–176.3） | 0 / 0 | 0 |
| 普通本机保存（单次） | 2.1 ms | 0 / 0 | 0 |

仅回执仍需原子写入完整已确认基线，因此不是零成本；普通本机保存不读取或重写大同步快照。计时包括事务及必要页面确认，不含 `readSync`、flight 构造、网络和 Firestore 成本；这不是历史版本对比，也不是手机性能结果。真正云端业务变化继续完整应用，避免为优化牺牲一致性。
